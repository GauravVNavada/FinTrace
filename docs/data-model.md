# FinTrace Data Model Evolution

**Status:** Sprints 1–7 local workflow boundary implemented · 2026-08-31

This document defines the data ownership introduced by the upload-driven product evolution. `docs/schema.md` remains the detailed canonical schema and migration authority; this file explains the workflow-level model and its boundaries. Fresh synthetic generation creates source files through the same `SourceFile` boundary; it is not a separate data model.

## Domain objects

### FinancialInvestigation

The top-level workspace for one organization's analysis of a defined period. It owns the uploaded sources, confirmed interpretation, dataset versions, reconciliation runs, derived exceptions/patterns, and scoped audit history.

Minimum fields:

```text
id, organization_id, name, description, period_start, period_end,
base_currency, status, created_by, created_at, updated_at
```

### SourceFile

Metadata and storage lineage for one uploaded CSV/XLSX file. Original filenames are display metadata only; storage names are generated by the server.

```text
id, organization_id, financial_investigation_id, original_filename,
storage_reference, mime_type, size_bytes, row_count, column_count,
status, detected_source_type, classification_confidence, created_at
```

### SourceMapping and RelationshipProposal

These capture human-confirmed interpretation of heterogeneous sources. A mapping may ignore a column, but required canonical fields must be resolved before normalization. Relationship proposals retain deterministic evidence and optional semantic interpretation; medium/low-confidence proposals are never silently accepted.

### DatasetVersion

An immutable processing snapshot containing normalized records and their lineage. Reconciliation runs always reference a dataset version; later uploads create a new version rather than mutating a completed run.

### ExceptionInvestigation

The existing child workflow for one unresolved exception. It owns bounded tool calls, structured evidence-backed output, verification, recommendation, and review state. It is not the same thing as `FinancialInvestigation`.

### ReconciliationRun and EvaluationRun

`ReconciliationRun` is one deterministic execution against a `DatasetVersion`. `EvaluationRun` is a benchmark execution against hidden ground truth. Neither object may be used as a generic container for the other.

## State boundaries

```text
FinancialInvestigation:
 DRAFT → SOURCES_UPLOADED → MAPPING_REQUIRED → RELATIONSHIP_REVIEW
        → READY_TO_BUILD → PROCESSING → RECONCILED | FAILED

SourceFile:
 UPLOADED → ANALYZING → MAPPING_REQUIRED → READY | FAILED

RelationshipProposal:
 PROPOSED → ACCEPTED | EDITED | REJECTED
```

Unknown and ambiguous outcomes remain explicit. No normalization or reconciliation step may guess a required relationship.

## Lineage requirement

Every normalized value that originated in an upload must be traceable to `source_file_id`, source row number, and the original source identifier. Raw files are not passed to the AI provider wholesale and are not treated as instructions.

## Migration boundary

Sprint 1 implemented `financial_investigations` and `source_files` in migration 005, plus indexes and organization-scoped constraints required for create/list/get/upload/list-source/delete operations. Sprint 2 implements bounded `source_analyses` and `source_mappings` in migration 006. Migration 007 implements deterministic `relationship_proposals` from confirmed canonical join fields; proposals require explicit acceptance or rejection. Migration 008 implements immutable dataset versions and normalized records with source-file, row, column, and source-record lineage. Migration 009 implements investigation-scoped reconciliation runs and per-order deterministic results linked to the dataset version. Migration 010 implements durable uploaded-exception investigations with bounded response state. Migration 011 makes uploaded-result approval requests durable while preserving canonical exception compatibility. Sprint 7 source generation reuses these tables and does not introduce a bypass or a second persistence path.
